# Container builds and dependency updates

All dependency/build/test commands run through Compose. Use `npm ci` for the committed package/lockfile pair; use an explicit Docker-based dependency update to change that pair together. Do not copy local `node_modules`, `.next`, coverage, database archives, backups or media into image contexts. The root `.dockerignore` excludes these while retaining application public assets, Prisma migrations, package manifests and build scripts. Source media remains a read-only runtime bind mount.

## Verified base references

Build/dependency stages and development command services use full Node **26.12.1 on Debian trixie**, pinned to multi-platform index `sha256:a98e6fda54fdbb22d4238054cca9a2a113bcd1191c09193a535aae22f400aa8e`. Production runtime, migration and browser-runner stages use the matching **trixie-slim** variant at `sha256:36793bcbb160a6a16cede1e62b93f84e26b78a972a8a4c0b879c1c12f22761ec`. Slim explicitly installs CA certificates/OpenSSL and role-specific media/browser packages. Its initial HTTPS apt request uses Node’s bundled Mozilla roots with an explicit CA path until the distribution certificate package is installed; certificate verification stays enabled. All database services use MariaDB **13.0.2 on Ubuntu resolute**, pinned to index `sha256:0e4bb0f339feba125d1154fbacd36c16ec8518f52e44e1f82ecec7d6771caf39`. These exact tags/digests were checked against the registry on 2026-10-24; they retain the runtime/database versions used in the preceding isolated recovery and release tests.

Upstream references: [Node official image variants](https://hub.docker.com/_/node), [MariaDB official image](https://hub.docker.com/_/mariadb), [Node releases](https://github.com/nodejs/node/releases). A digest prevents tag movement; it also requires deliberate updates.

At least monthly, and promptly for upstream security fixes, the maintainer checks upstream releases, resolves candidate exact OS/patch tags with `docker buildx imagetools inspect`, and updates the relevant image references in `docker/base-images.yml`. Keep the full and slim Node variants on the same patch release. Regenerate the lockfile in the pinned Node command container for intentional dependency changes. Keep Prisma CLI/client on the same exact version (currently 5.8.1), Node typings on major 26 and Next ESLint tooling aligned with Next (currently 16.4.3, with React/React DOM 19.3.1). Build from a clean context, generate Prisma, migrate/seed a fresh isolated DB, check the final native/media dependencies, run fixture indexing plus API/browser/Jest checks and repeat the release identity/failure checks before publishing. Retain the previous release manifest until deployment acceptance; follow the [database lifecycle runbook](database-lifecycle.md) before a database upgrade. Never reset a deployed DB to validate an update.

## Central base image configuration

[`docker/base-images.yml`](../docker/base-images.yml) owns the full and slim Node image pins and the MariaDB image pin. All three application Compose files import its build arguments using `extends`; development command services also inherit its full image. All three database services inherit the shared MariaDB image using `extends`; database upgrade and host-access overrides retain this pin. Existing Compose commands and environment files need no changes. Dockerfiles accept `NODE_IMAGE` and/or `NODE_SLIM_IMAGE` before `FROM`; direct Docker builds must supply the corresponding build arguments explicitly. Use Compose builds to apply the central pins automatically.

## Packaging

Production uses Next.js standalone output and starts the traced `server.js` with an exec-form shell handoff after runtime configuration validation. The final non-root image contains the traced runtime modules/pages, explicitly copied public and `.next/static` assets, generated Prisma client/engines, bcrypt native package and scheduler/config validator. It omits the complete development/build dependency tree and compiler caches. `HOSTNAME=0.0.0.0` makes the standalone server listen on the container interface; cookie security remains controlled independently by `SESSION_COOKIE_SECURE`. FFmpeg/ffprobe come from Debian's `ffmpeg` package in app/development images. Prisma generation uses the locked local CLI and native Debian target before runtime packaging. Migration and test builds retain their role-specific tools; production images have no migration CLI or TypeScript compiler. Tests reuse the production migration Dockerfile.

Changing application source reuses the dependency layer; changing a package manifest or lockfile invalidates it. Prisma schema changes invalidate generation. Fresh contexts are authoritative; existing development bind-mounted dependencies are not silently replaced when these images are rebuilt. Refresh a development installation deliberately with `docker compose run --rm dependencies npm ci` and `docker compose run --rm dependencies npx --no-install prisma generate` after stopping consumers that use its dependency tree.

## Browser tests and platform scope

Test images install Debian's system Chromium and set `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium`; media tools stay in application images because fixture setup calls the background HTTP API. Browser downloads are disabled for every dependency-install stage and the development command service. Jest and the TLS regression fixture use that configured path. Browser/API tests use the Compose network alias `web.test` for HTTP: Chromium upgrades the `.app` name to HTTPS through HSTS, so the bare service name `app` cannot serve as the HTTP browser URL. Background requests continue to use service DNS. The locked yargs 17.7.3 override supplies the explicit CommonJS entrypoint needed by Puppeteer/Jest under Node 26, replacing the extensionless CommonJS entrypoint in 17.7.2 ([upstream fix](https://github.com/yargs/yargs/releases/tag/v17.7.3)).

Validation is performed on Linux amd64. Debian Chromium provides an alternative to the previous amd64-only Google Chrome repository. The Debian media tools also support ARM; bcrypt/Prisma and the complete application still require target-architecture validation before ARM support is claimed. Browser apt packages follow the pinned Debian distribution's security repository; test images are not claimed to be byte-for-byte reproducible over time. bcrypt 6.0.0 packages its Node-API prebuilds in its integrity-checked npm tarball instead of fetching them from GitHub during installation ([upstream change](https://github.com/kelektiv/node.bcrypt.js/releases/tag/v6.0.0)). Media tools are installed through the distribution package manager. The final-image smoke check verifies bcrypt and both media tools actually execute.

## Build cache and migration dependency maintenance

Dependency installs and production pruning mount `/root/.npm` as a shared BuildKit cache instead of embedding downloaded package archives in image layers. Next compilation mounts `.next/cache`, scoped to Node 26 and target architecture; compiler cache contents are not shipped. Normal layer caching still avoids rerunning unchanged steps. A missing or discarded cache must remain a supported build path. Application compilation copies required source/assets/configuration explicitly, so test-only changes do not recompile production. Only `schema.prisma` precedes generation; seed/migration changes are copied later into the migration image.

Migration/bootstrap has its own exact manifest and lockfile in `docker/prod/migration/`. It includes Prisma CLI/client, bcrypt and TypeScript seed execution support, without the application's browser/test/UI dependencies. The seed imports the shared `passwordHelper.ts`; the user utility re-exports its existing API. Keep Prisma, bcrypt, TypeScript and Node typings aligned with the application when intentionally updating them. Regenerate this lockfile in Docker, for example:

```sh
docker compose run --rm --no-deps --user "$(id -u):$(id -g)" --workdir /work --volume "$PWD/docker/prod/migration:/work" dependencies npm install --package-lock-only --ignore-scripts --no-audit --no-fund --cache /tmp/npm-cache
```

Run migration/seed acceptance after dependency updates. Optional layer-cache import/export for replacement builders is described in [the release runner guide](../scripts/build/README.md). Cache mounts persist with their builder; exported layer caches do not automatically transfer those mutable mount contents to another builder. Protect persistent cache directories, scope them per repository/platform, and manage retention separately from disposable task resources.

Build-time Debian mirror selection and bounded download retries are documented in the release runner guide. The main archive mirror can change independently of the default security repository; signed metadata and HTTPS verification remain required.


## Next.js 16 validation gates and sessions

Next.js 16 no longer runs lint during builds. The production builder explicitly runs `npm run lint` over source and tests before `npm run build`; builds enforce TypeScript checks. For bind-mounted development, use Docker `npm run lint` and `npm run typecheck` (which generates Next route types first). Development and builds explicitly select Webpack to retain file polling. Both configurations enable type validation and the production configuration retains standalone output.

The application uses iron-session 9 on Node, including the Next `proxy.ts` cookie adapter. The cookie name, secret setting, 14-day duration and flags remain unchanged. Pre-v8 cookies are unreadable after this upgrade, so users must sign in once. Keep the previous release manifest/images for rollback; cookies minted by the new version need a fresh login after rollback to v6. The application typechecker uses ESNext/Bundler resolution; ts-node seed/background commands retain a CommonJS/Node override.
