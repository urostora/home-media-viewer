# Background processing baseline

From the repository root:

```sh
python3 scripts/benchmark/run.py --output /tmp/hmv-benchmark-results
```

Requires Docker Compose and Python 3.9+ for Docker orchestration. Application code, media tooling, Prisma, fixture generation, and probes run in containers. The runner builds the **working tree**, runs production-mode source modules with two workers, and starts a production Next.js foreground app. No host ports are published. Random credentials, database/storage volumes, image tags, and the copied/generated source tree belong to a unique project. Existing development resources and `test/files` are preserved; all source mounts used during measurements are read-only. Setup stops on failure, and cleanup runs on exit. Keep the output directory as the benchmark artifact; it must not already exist. `--repeats` defaults to three.

Audit a result file and generate a summary through the existing tooling container:

```sh
docker compose run --rm --no-deps -T -v "$PWD:/workspace:ro" dependencies node /workspace/scripts/benchmark/summarize.cjs < /tmp/hmv-benchmark-results/results.json
```

Setup builds images, starts and waits for MariaDB, applies migrations, explicitly seeds the administrator, generates fixtures, starts the foreground app, and waits for readiness. The seeded login is used by foreground album-search probes; session cookies stay in memory. The fixture manifest records neutral paths, sizes, and hashes. Fixtures include 500 small unsupported files, 60 small images, four large images, twelve directory levels, twenty sibling directories, two existing test images, two existing test videos, and one synthetic video. Three overlapping albums expose repeated traversal. Size-change and same-size-change cases alter only disposable JPEG trailing bytes and mtime.

Each run starts a fresh benchmark process/container and excludes module loading, database connection, snapshot queries, readiness warmup, and probe login from elapsed time. The harness loads existing application modules unchanged and intercepts Prisma query events, Jimp reads, and media command dispatch. The timing recorder does not record SQL text/parameters, credentials, or extracted media metadata. Validation-mode query-plan artifacts separately retain SQL and bound synthetic fixture parameters, as described below. Discovery and full measurements call the shared production runner. Discovery now uses resumable directory tasks and caches one physical enumeration per run, including overlapping album scopes. Historical I1a discovery records used the previous root/directory helpers; keep that methodology difference visible when comparing them. Full runs select unique file records across overlapping albums. Separate stage outcomes are combined per file for the recorder’s media-job accounting.

`results.json` records elapsed time, throughput, attempted/succeeded/failed media and directory jobs, thumbnail publications, deferred metadata, before/after metadata and thumbnail counts, data SQL statements and summed Prisma query-event durations, Jimp reads, FFmpeg/ffprobe invocation counts and summed wall durations, CPU, RSS, container memory, event-loop delay, and HTTP latency distributions/statuses. SQL timings come from the Prisma engine/adapter query events rather than a separate server-side profiler; precision varies by engine, and overlapping durations can sum to more than wall time. Counts exclude transaction-control SQL and adapter-generated commit/rollback comments. SQL counts include indexing-process readiness queries during the measurement; foreground queries use a separate client and are excluded. Cgroup CPU includes subprocesses and the probe. Sampled RSS covers the measurement window; lifetime peak RSS and cgroup memory peak also include startup. No image-decode count is inferred from subprocess counts. Oldest pending creation age (snapshots and queue observations) is only an approximation: the schema has no enqueue timestamp. Throughput counts successful media jobs, including filesystem-only processing of unsupported files, so compare it only with the same fixture manifest. Use per-type decode/subprocess counts alongside it.

Health handlers run on a harness HTTP server in the indexing process, while the foreground app serves real readiness and authenticated album-search requests. An independent child process probes every 100 ms with a five-second timeout, so indexing event-loop stalls remain visible. Short runs can have very few samples: inspect sample counts and maxima; their p95 is not a production latency estimate. Readiness has the application's five-second cache. An indexing failure or HTTP failure fails the run.

The recorder now accepts `metadata` and `thumbnails` modes against existing discovered records. The default repeated matrix retains the original discovery/full scenarios; use `--measure-stages` for repeated independent-stage measurements before claiming a stage-performance baseline. Validation mode smoke-checks both real independent stages. Do not present coupled full runs as stage measurements. Baselines are descriptive; numerical improvement targets require reviewing these results and agreeing targets. Re-run with the same image/tool versions, fixtures, resource limits, and host load for comparisons. Kernel caches are not flushed; initial runs are fresh database imports, not guaranteed cold-storage reads. This small fixture suite does not establish production-library scaling or emulate slow network storage. No scheduler runs during these measurements.

Use `--validate-stages` to run migration preservation and application acceptance checks instead of the repeated benchmark matrix. This starts production app/background services and records `acceptance.json`, including two independent-stage recorder smoke runs, `discovery.json` for discovery correctness/scaling, and `media-queue.json` for bounded paging, continuous workers, fair continuation, deadline/shutdown/rejection handling and virtual large-queue heap measurements. The virtual check uses exposed GC only in the test worker; the application does not require it. See [background processing](../../docs/background-processing.md). The benchmark worker uses the production UID so shared generated storage remains writable to both app roles. Benchmark preparation clears both task-owned cursor tables so each initial-import repetition starts fresh.

I6 processor checks (`docker/test/media-processors.cjs`) also run in validation mode. They compare independently resized image variants and split-frame video previews with the prior generation commands, check EXIF/video rotation, custom JSON tags and rational frame rates, invocation counts, corrupt inputs, large images, tool limits, and cancellation. Sources remain read-only; generated checks use a private temporary directory that is removed on completion.

Add `--measure-stages` to include three repeated discovery → metadata → thumbnails sequences (or the selected `--repeats`) after the standard matrix. Each sequence starts with a fresh task library; both media measurements run against existing discovered records and select only their own pending work. These measurements do not imply agreement on numerical performance targets.

I7 database checks also run in validation mode. `database-writes.json` records multi-row metadata statement counts and real transaction rollback, source-change/retry, Manual/Legacy protection, typed-value/ID preservation, atomic discovery batches, raw-SQL deadlock handling and five-connection pool checks. `query-plans.json` retains the actual production Prisma page SQL/bound fixture parameters, before/after `EXPLAIN FORMAT=JSON` and three `ANALYZE FORMAT=JSON` repetitions per scenario. The 32,768-file/49,664-membership library covers sparse and dense queues, overlapping and small albums, first/resumed pages and refresh. Indexes are temporarily removed/recreated only inside that disposable database; the original migrated schema is restored before cleanup. SQL artifacts contain neutral synthetic identifiers, never shared-library queries or credentials. The recorder counts scalar `updateMany` stage completions as well as returned-row updates.

I8 validation adds `run-observability.json`: durable/fresh-process and authenticated status reads, independent stage failures, partial/drained/shutdown distinctions, uncertain counts on infrastructure errors, journal-write failures, nested run protection, discovery continuation, real SIGKILL with fail-closed lock, and 100-record history/temporary-write cleanup. Run scheduler timer/body-abort/backoff checks separately with `docker/test/scheduler.test.mjs` (Node `--experimental-vm-modules`); operations and shutdown regressions use their existing Docker checks.

Use `--budget-seconds 120` for a comparison with the production default dispatch budget; default remains 600 for historical benchmark compatibility. The requested value is recorded as `dispatchBudgetSec` and forwarded to the real runner. The standard fixture matrix must still drain before comparing throughput; short intentionally partial runs describe budget behavior instead. Durable journal checkpoints are active during the measurements, so their filesystem work is included.

I10 validation adds `video-thumbnail-time.json`: strict runner/API/CLI time options; changing-frame, zero/fractional and default parity at all sizes; one limited timing probe/one generation invocation; moving/rotated frame parity; explicit regeneration and pending selection; invalid range/unknown duration/missing frame/decode failures preserving usable previews and metadata. Custom-only requests use a timing probe without full metadata extraction. Successful explicit video selections are saved as Manual Float metadata under `video_thumbnail_time` (seconds); later regeneration uses the saved time unless explicitly overridden. Metadata refresh preserves this selection. An invalid saved time fails while any existing thumbnail is available; with no thumbnails it generates the default first frame and retains the saved value. Failed generation/publication does not save a new selection. The checks cover saved-time reuse through metadata refresh, album/pending processing and CLI, partial/missing preview sets, and database/source-change rollback. Fixtures generated by these checks are temporary and removed before task teardown.

Repeated measurements reset only the guarded fixture login budgets between scenarios. SQL statement metrics exclude transaction-control commands so Rust and driver-adapter runs have comparable query-log coverage.
