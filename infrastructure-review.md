## 2. Critical: production startup conflicts with non-root execution — finished

Original evidence (before this task): `docker/prod/app/Dockerfile` ended with `USER node` followed by `CMD env >> /etc/environment && service cron start && npm start`.

The node user normally cannot append to root-owned `/etc/environment` or start system cron. Because commands are joined with `&&`, the first failure prevents Next.js from starting. Both production services and the test Compose app/background use this image.

Recommendations:

- **finished** — Keep the application non-root and give the web container a direct foreground entrypoint, preferably an exec-form command with correct signal forwarding.
- **finished** — Move scheduling into a separate foreground scheduler that can run without root, or a documented host scheduler calling the internal background service. The indexing HTTP service can remain separate from the public web service.
- **finished** — Pass only required variables to the scheduler. Stop dumping all credentials into `/etc/environment`.
- **finished** — Send scheduler output to container stdout/stderr. The former production `/var/log/cron.log` output has been removed; scheduler logs now go to container stdout/stderr.
- **finished** — Verify a fresh storage volume and an existing volume are writable by the application UID. Image-layer ownership does not repair existing volume permissions.

The restarted scheduler then processed an additional photo at its unchanged three-minute interval.

## 3. High: startup and migrations have no reliable ordering — finished (migration/bootstrap scope)

Original evidence (before task 2): all Compose dependencies use short-form `depends_on`; neither migration Dockerfile declares a migration command; app/background depend only on `db`. The production README migration command lacks `run` and a service name. Production migration receives only `DATABASE_URL`, and no explicit administrator bootstrap is documented.

Consequences: services can start before MariaDB accepts connections or before schema deployment completes. Starting the migration container by itself does not explicitly execute `prisma migrate deploy`. A fresh database can lack an administrator even after migrations.

Recommendations:

- **finished** — Add a MariaDB readiness check that verifies initialization and connectivity, using the selected image's documented healthcheck tooling.
- **finished** — Give the migration service an explicit `npx prisma migrate deploy` command and `restart: "no"`.
- **finished** — Either gate web/background on migration `service_completed_successfully`, with migration gated on database `service_healthy`, or use an explicit release script that waits for DB readiness, runs migration successfully, then starts application services. [Compose startup ordering](https://docs.docker.com/compose/how-tos/startup-order/)
- **finished** — Repair the production README migration command and document database readiness gating, explicit bootstrap, and the upgrade sequence.
- **finished** — Define a separate, explicit first-install administrator bootstrap. Use `ADMIN_EMAIL` consistently for lookup and creation, and reject missing credentials instead of using fallback passwords.
- **finished** — Add bounded retry/reconnection behavior for temporary DB outages; startup ordering alone does not handle later failures.

Implementation: all three Compose configurations give MariaDB a `healthcheck.sh --connect --innodb_initialized` check. Migration waits for `service_healthy`, runs `npx --no-install prisma migrate deploy`, and has `restart: "no"`. App/background wait for `service_completed_successfully`; development has a dedicated migration job using installed bind-mounted dependencies. Both migration Dockerfiles declare the same default command. Production migration receives explicit administrator settings for a separately invoked seed. The seed requires nonempty credentials, creates the configured email, preserves existing active administrators/passwords, and refuses implicit promotion or reactivation. Shared Prisma middleware retries only connection failures on ordinary reads outside transactions, at most twice with 250/500 ms delays; initialization error codes are also recognized. Writes, raw SQL and transactions are never replayed. README installation and upgrade procedures now separate schema deployment from bootstrap and stop existing consumers before upgrading.
